# Migration poetry + requirements.txt → uv (unique)

## Contexte

Le projet utilise actuellement deux outils Python distincts pour deux besoins différents :

- **poetry** (`pyproject.toml`, `package-mode = false`) gère 4 dev-deps : ruff, pylint, pyright, prek.
- **pip + `requirements.txt`** installe l'environnement Home Assistant complet (HA lui-même +
  ~45 paquets requis par les intégrations chargées par `default_config:`) pour faire tourner
  `scripts/develop` (un vrai serveur HA local servant à tester l'intégration). Ce fichier mélange
  des paquets pinnés à la main (homeassistant, prek, pylint, pyright, ruff en double avec poetry)
  et un bloc auto-régénéré par `scripts/update_requirements.py`.

L'utilisateur veut unifier entièrement sur **uv** : un seul outil, un seul lockfile
(`uv.lock`), plus rapide, syntaxe `pyproject.toml` PEP 621 native (poetry émet actuellement des
warnings de dépréciation `[tool.poetry.*]` vs `[project.*]`, vus lors de `poetry check`).
**`requirements.txt` est abandonné** - son contenu (deps HA + default_config) migre dans un
groupe de dépendances dédié `ha` en TOML, aux côtés du groupe `dev` existant.

`uv` est déjà installé dans ce devcontainer (`/home/vscode/.local/bin/uv`, v0.11.25), donc la
migration ne nécessite pas de reconstruire l'image immédiatement pour tester - mais le
Dockerfile/devcontainer.json doivent être mis à jour pour que ce soit reproductible pour tout
nouvel environnement.

Aucune mention de poetry ni de requirements.txt dans CLAUDE.md → pas de doc projet à corriger
pour ce fichier précis.

## Approche

### 1. `pyproject.toml` - PEP 621 + deux groupes de dépendances (`dev`, `ha`)

Remplacer les sections `[tool.poetry]` / `[tool.poetry.urls]` / `[tool.poetry.dependencies]` /
`[tool.poetry.group.dev.dependencies]` par :

```toml
[project]
name = "betaseries-for-home-assistant"
version = "0.0.0"
description = "..."  # reprise telle quelle
readme = "README.md"
requires-python = ">=3.14,<3.15"
license = "MIT"
authors = [{name = "Bastien Gautier", email = "contact@bastiengautier.com"}]
maintainers = [{name = "Bastien Gautier", email = "contact@bastiengautier.com"}]
classifiers = [...]  # inchangé

[project.urls]
Homepage = "https://github.com/bastgau/ha-betaseries"
Documentation = "https://github.com/bastgau/ha-betaseries"
Repository = "https://github.com/bastgau/ha-betaseries"
"Bug Tracker" = "https://github.com/bastgau/ha-betaseries/issues"
Changelog = "https://github.com/bastgau/ha-betaseries/releases"

[dependency-groups]
dev = [
  "prek==0.2.28",
  "pylint==4.0.4",
  "pyright==1.1.411",
  "ruff==0.15.1",
]
ha = [
  "homeassistant==2026.7.0",
  # --- generated by scripts/update_requirements.py, do not edit below by hand ---
  "aiodhcpwatcher==1.2.7",
  "aiodiscover==3.3.2",
  "aioesphomeapi==45.3.1",
  ... (~45 paquets, contenu identique à l'actuel requirements.txt)
]

[tool.uv]
package = false  # projet non buildé/publié (custom component HACS, pas une lib PyPI)
```

Les sections `[tool.ruff]`, `[tool.ruff.lint]`, `[tool.pylint."MESSAGES CONTROL"]` restent
**inchangées** (indépendantes de poetry/uv/requirements.txt).

### 2. Suppression de `requirements.txt`

Fichier supprimé entièrement. Son contenu est repris tel quel (mêmes pins de version) dans
`[dependency-groups.ha]` de `pyproject.toml`.

### 3. `scripts/update_requirements.py` - réécrire le groupe TOML au lieu du fichier requirements.txt

Adapter le script pour :

- lire/écrire `pyproject.toml` via `tomlkit` (préserve formatage/commentaires - déjà une dépendance
  transitive de poetry, sera ajoutée explicitement si besoin) au lieu de faire du texte brut sur
  `requirements.txt`.
- remplacer uniquement les entrées du groupe `ha` situées après le marqueur `homeassistant==X.Y.Z`
  (garder ce pin en tête, généré séparément - c'est le seul pin manuel du groupe, le reste est
  auto-généré depuis les manifests HA installés).
- la fonction `rewrite_requirements_file` devient `rewrite_ha_dependency_group`, ciblant
  `pyproject.toml` au lieu de `REQUIREMENTS_FILE`.
- Constante `REQUIREMENTS_FILE` renommée/retirée, remplacée par `PYPROJECT_FILE`.

### 4. `scripts/update-requirements` - mise à jour du message

Le script bash change juste le message affiché ("Regenerating requirements.txt" →
"Regenerating the `ha` dependency group in pyproject.toml") ; il continue d'appeler
`update_requirements.py`, inchangé sinon.

### 5. `scripts/setup` - remplacer pip par uv sync

```bash
# avant
python3 -m pip install --requirement requirements.txt

# après
uv sync --group ha --group dev
```

Un seul appel `uv sync` installe à la fois l'environnement HA complet et les dev-deps
(ruff/pylint/pyright/prek), dans le même `.venv` géré par uv. Plus simple que l'ancien script
(qui ne gérait que l'environnement HA, les dev-deps poetry étant installées à part).

### 6. `scripts/develop` - passer par `uv run`

```bash
# avant
hass --config "${PWD}/config" --debug

# après
uv run hass --config "${PWD}/config" --debug
```

Garantit que `hass` s'exécute dans le `.venv` géré par uv (plus de dépendance à une install
système globale). Idem pour l'appel `hass --script ensure_config` un peu plus haut dans le script.

### 7. `.devcontainer/Dockerfile` + `devcontainer.json` - installer uv via script Astral

Décidé : install script officiel Astral dans le `Dockerfile` plutôt qu'une feature devcontainer
communautaire tierce (évite une dépendance à un mainteneur non-Microsoft/Astral).

`.devcontainer/Dockerfile` - ajouter après les `apt-get install` existants :

```dockerfile
# Install uv (manages dev-deps and the HA runtime env, both declared in pyproject.toml)
RUN curl -LsSf https://astral.sh/uv/install.sh | sh -s -- --install-dir /usr/local/bin
ENV PATH="/usr/local/bin:${PATH}"
```

`.devcontainer/devcontainer.json` - retirer l'entrée
`"ghcr.io/devcontainers-extra/features/poetry:2"` de `features` (plus besoin, uv vient du
Dockerfile). Les autres features (github-cli, node, rust) restent inchangées.

### 8. `.gitignore` - vérifier les entrées lockfile

`uv.lock` **ne doit PAS être gitignoré** (comme `poetry.lock` ne l'était pas - le lock doit être
committé pour la reproductibilité). Vérifier qu'aucune règle `*.lock` trop large n'existe déjà.

### 9. Nettoyage final

- Aucun `poetry.lock` trouvé lors de l'exploration (jamais généré, aucun commit n'a encore eu
  lieu) - rien à supprimer de ce côté.
- Générer `uv.lock` via `uv lock` une fois `pyproject.toml` migré.
- Vérifier toute référence résiduelle à `requirements.txt` dans le repo (scripts, CI, README,
  .pre-commit-config.yaml) et les mettre à jour/retirer.
- `.devcontainer/devcontainer-lock.json` référence encore la feature poetry (hash résolu) - ce
  fichier est auto-généré par l'extension devcontainer et se régénérera tout seul au prochain
  rebuild une fois la feature retirée de `devcontainer.json` ; pas d'édition manuelle nécessaire,
  juste à noter comme non-vérifiable dans cette session (pas de rebuild possible).

## Fichiers modifiés

- `pyproject.toml` (sections poetry → PEP 621 + `[dependency-groups]` dev/ha + `[tool.uv]`)
- `requirements.txt` → **supprimé**
- `scripts/update_requirements.py` (réécrit pour cibler pyproject.toml au lieu de requirements.txt)
- `scripts/update-requirements` (message mis à jour)
- `scripts/setup` (pip install → `uv sync --group ha --group dev`)
- `scripts/develop` (`hass ...` → `uv run hass ...`)
- `.devcontainer/Dockerfile` (ajout install script uv)
- `.devcontainer/devcontainer.json` (retrait de la feature poetry)
- nouveau : `uv.lock` (généré, à committer)

## Vérification

1. `uv sync --group ha --group dev` → installe HA + deps default_config + dev-deps sans erreur
   (uv 0.11.25 déjà présent dans ce devcontainer, testable immédiatement).
2. `uv run python scripts/update_requirements.py` → régénère correctement le groupe `ha` dans
   `pyproject.toml` (vérifier le diff : mêmes paquets qu'avant, juste un format différent).
3. `scripts/setup` de bout en bout → s'exécute sans erreur.
4. `scripts/lint` → toujours vert (appelle `prek run ruff-check`, `pylint`, `pyright` directement ;
   fonctionne une fois les paquets dev installés dans le `.venv` actif - vérifier si le script doit
   préfixer ses appels par `uv run` pour cibler le bon interpréteur, sinon l'ajuster).
5. `scripts/develop` → démarre toujours `hass` correctement via `uv run`.
6. `grep -rn "requirements.txt"` sur tout le repo → zéro résultat restant (CI, README, scripts,
   pre-commit).
7. Le rebuild complet du devcontainer (validant le Dockerfile modifié) ne peut pas être testé
   dans cette session (uv est déjà présent dans le conteneur actuel, installé autrement) - sera
   à valider par l'utilisateur au prochain rebuild. Je le signalerai explicitement en fin de tâche.
